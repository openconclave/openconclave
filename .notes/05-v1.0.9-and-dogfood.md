## Side quest: the `/runs` page was slow

Mid-session the user observed the `/runs` UI page got noticeably slow while agents were running. Diagnosed in `packages/server/src/routes/runs.ts`:

```ts
.get("/", async (c) => {
  const allRuns = await db.select().from(runs).orderBy(desc(runs.createdAt)).limit(50);
  const allTasks = await db.select().from(agentTasks);  // ← unbounded!
```

`allTasks` pulled every row from `agent_tasks` ever, then aggregated cost per run in a map. As the DB grew, the query got linearly slower, and during active agent runs it competed with active INSERT/UPDATE on the same table. Classic.

Fix: filter to only the 50 runs we're actually rendering:

```ts
const runIds = allRuns.map((r) => r.id);
const allTasks = runIds.length > 0
  ? await db.select().from(agentTasks).where(inArray(agentTasks.runId, runIds))
  : [];
```

One line and an `inArray` import. Committed as `3eb330a`.

(Also noted a separate UI bug: the Runs page doesn't re-fetch while agents are working. That's not the same problem — that's a missing WebSocket subscription on the client side. Noted for a follow-up session.)

## Run 60 — `oc_review` on `code.ts`

Picked `packages/server/src/engine/nodes/code.ts` (83 lines) as the target. Small enough that the pipeline overhead is visible, big enough that it has real concerns worth reviewing.

Ran in parallel with run 59 to test that two conclaves running simultaneously don't interfere. They didn't.

**Result**: 0 blockers, 4 major, 2 minor, 1 nit — 7 findings on 83 lines. Review file: `.reviews/20260412-015101-code.ts.md`.

The four majors were all real:

1. **Pipe deadlock on heavy stderr** (code.ts:69–71). `proc.stdout` and `proc.stderr` drained one after the other. OS pipe buffer is ~64KB; any subprocess writing more than that to stderr before its final stdout write would block forever. Fix: `Promise.all` the two reads. The Best Practices agent found the [Old New Thing article](https://devblogs.microsoft.com/oldnewthing/20110707-00/?p=10223) on this classic bug and captured it as a new KB lesson.

2. **`Bun.file().size` dead catch block** (code.ts:23–26). The code assumed `Bun.file(missing).size` would throw. It doesn't — it returns `0`. Per [Bun issue #589](https://github.com/oven-sh/bun/issues/589). On non-standard Windows git installs (Chocolatey shim, custom prefix, nested mingw64), `resolveGitBash()` silently returned a phantom path, and every `bash` code node failed cryptically at spawn. Fix: use `existsSync` explicitly.

3. **`...process.env` leak to user subprocesses** (code.ts:54). Wholesale process.env spread into code-node subprocess environments, meaning user Python/node/bash code could trivially read `process.env.ANTHROPIC_API_KEY` or any other secret. Cross-file pattern: same fix as `runtime.ts` already had (`buildSubprocessEnv`) — the review explicitly cited the existing KB lesson and recommended importing the helper instead of reimplementing.

4. **`OC_API_URL` built from `PORT` env var** instead of `process.env.OPENCONCLAVE_URL` like every other caller in the codebase. Breaks reverse-proxy deployments.

Plus two minors and a nit of varying severity.

## Manual fixes to code.ts (commit `b197572`)

Applied 3 of the 4 majors by hand since they were 5-line fixes each and I was already waiting on run 59 to complete:

```ts
// Concurrent drain prevents pipe deadlock
const [stdout, stderr] = await Promise.all([
  new Response(proc.stdout).text(),
  new Response(proc.stderr).text(),
]);

// existsSync for git bash detection
if (existsSync(candidate)) return candidate;
return "bash";

// buildSubprocessEnv for code-node env
env: buildSubprocessEnv({
  INPUT: inputStr,
  PYTHONIOENCODING: "utf-8",
  PYTHONUTF8: "1",
  ...(context ? {
    OC_API_URL: process.env.OPENCONCLAVE_URL ?? "http://localhost:4000",
    OC_CONCLAVE_ID: String(context.conclaveId),
    OC_RUN_ID: String(context.runId),
    OC_NODE_ID: context.nodeId,
  } : {}),
}),
```

Deferred the `INPUT` env-var redundancy finding (minor) — existing conclaves read it from `os.environ.get('INPUT')` and removing it would break them silently.
